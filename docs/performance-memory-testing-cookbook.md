# 性能与内存测量 Cookbook

> **定位**：操作手册，自包含。照着做，一次测对。
> 本文只回答一件事：**某个指标，用什么、怎么跑、凭什么判定**。
> 环境约束见 §6——不了解它会设计出原理上无法成立的判据。

---

## 1. 两条判别原则

动手前先用这两条判断，能避免绝大多数无效测量。

### 原则一：先分清指标是不是依赖时间

| 类型 | 例子 | 含义 |
| --- | --- | --- |
| **时间无关量** | 分配次数、peak heap、体素计数、bounds、错误/泄漏有无 | 由**代码路径**决定。**可以降频测**，工具拖慢不影响结论 |
| **时间相关量** | 延迟、CPU%、吞吐、backlog | 由**执行速度**决定。**必须真实频率测**，且只能用零扰动工具 |

判别方法：问一句"**把程序放慢 10 倍，这个数字会变吗？**"
会变 → 时间相关量；不变 → 时间无关量。

### 原则二：重工具能不能上 = 工具开销 × 剩余预算

不是看工具轻不轻，是看**当前规模下回调还剩多少预算**。

```
剩余余量 = 1 − (callback p99 ÷ 周期预算)
可上的工具开销上限 ≈ 剩余余量
```

动手前先查当前规模的 callback p99 占周期比例，再决定能上哪种工具。
余量不足时有两个选择：**缩小规模**，或**改走降频路线**。

## 2. 两条测量路线

全部指标由两条路线覆盖。**两条路线跑同一个冻结场景、同样的 revision 数，
只有墙钟速度不同**——因此逻辑工作量完全一致，结论可以互相印证。

| | **路线 A：真实频率** | **路线 B：降频** |
| --- | --- | --- |
| 频率 | 系统标称频率 | 降到工具开销落进预算内 |
| 工具 | pidstat、smaps_rollup、UST 探针、oracle | ASan、LSan、Memcheck、Heaptrack、Callgrind |
| 工具扰动要求 | **必须 ≈0** | 不限 |
| 覆盖 | CPU%、延迟、实时性、内存占用、泄漏斜率、容量 | 内存错误、未初始化读、分配栈、函数级热点 |
| 硬性要求 | 不得引入任何有扰动的工具 | **必须跑满与路线 A 相同的 revision 数** |

### 降频倍数怎么定

**不写死倍数**，按下式推：

```
降频倍数 ≥ 工具开销倍数 ÷ 剩余余量
```

例：工具开销 50×、当前余量 0.9 → 降频 ≥ 56 倍。
不同工具差别极大（ASan 约 2×、Valgrind 系 10–50×），必须逐工具算。

**降频后必须核对**：`observation 数`、`revision 数`、`final_known` 与路线 A 一致。
不一致说明逻辑工作量不同，结论不可比。

### 降频路线测不到什么

以下三类**只能走路线 A**，降频后会失真或永远不发生：

- 延迟、CPU%、吞吐
- **并发竞态**（时序变化会改变竞态窗口）
- **背压与队列积压**（降频后不会积压）

## 3. 指标 → 测量方法

| 指标 | 路线 | 工具 | 负载与时长 | 判定依据 |
| --- | :---: | --- | --- | --- |
| **CPU 使用率** | A | pidstat | 真实频率，≥300 s，**三轮独立** | 均值；仅采信 ≥30% 的差异（见 §6） |
| **实时性（跟不跟得上）** | A | observation vs revision 计数偏斜 + rev/s 曲线 | 真实频率，全窗口 | 偏斜门；rev/s 应恒等于标称频率 |
| **每帧延迟 + 阶段分解** | A | LTTng-UST 编译期探针 | 真实频率，≥300 s | p50/p95/p99；**同 run 内的阶段占比最可信** |
| **内存占用 RSS/PSS/USS** | A | smaps_rollup | 真实频率，≥300 s，三轮 | 峰值与均值；**多节点求和必须用 PSS** |
| **泄漏（稳态）** | A | 三轮独立线性回归斜率 | **bounded**，≥300 s | 斜率 < 阈值（当前 1024 KiB/min） |
| **每单位工作的内存成本** | A + B | Δmemory ÷ Δknown_cells | **expanding** | **双工具交叉**：smaps 与 Heaptrack 应一致 |
| **容量上限** | A | 阶段 p99 vs 周期预算 + rev/s 曲线 | expanding，跑到掉队 | p99 逼近预算即拐点 |
| **正确性 / 等价** | A + B | oracle 每 100 revisions 逐点比对 | **所有 run 强制** | counts / bounds / stamp 精确一致 |
| **堆分配行为（谁在分配）** | B | Heaptrack + 分配栈 | 降频，**跑到目标规模** | 分配次数、temporary **绝对量**、top 分配栈 |
| **越界 / UAF** | B | ASan | 降频，**跑到目标规模** | 零 error |
| **未初始化读** | B | Memcheck | 降频，**跑到目标规模** | 零 error |
| **CPU 函数级热点** | B | Callgrind 跑 ROS-free oracle ⚠️ | 离线，不限时 | 精确指令数排序（**无需 PMU**） |

> ⚠️ **Callgrind 一行为原理推荐，尚未在本仓库实测**。
> 依据：Callgrind 模拟指令计数，不依赖硬件 PMU，且热点排序是相对量、不需要实时。
> 已知限制：ROS-free oracle 不含 ROS 消息序列化路径，该段需另行覆盖。

### 两个容易错的读数

- **temporary 分配比例**：必须看**绝对量**，不能只看百分比。地图增长时总分配量会
  暴涨，比例被稀释，但绝对量可能没变。
- **每单位内存成本**：这是**含全部开销的等效成本**（数据结构 + 分配器开销 +
  碎片），不是数据结构的 `sizeof`。用于容量规划正确，当作结构体大小则错误。

## 4. 场景矩阵

| 场景 | 用途 | 必跑项 |
| --- | --- | --- |
| **bounded**（收敛到 plateau） | 稳态基线、泄漏判定 | 路线 A 全套 + 路线 B 全套 |
| **expanding**（持续扩张） | 每单位成本、容量上限、**大规模内存错误** | 路线 A 全套 + 路线 B **跑到目标规模** |

**硬性要求**：路线 B 的 expanding **必须跑到与路线 A 相同的体素规模**。
否则大规模区间在内存错误维度上没有覆盖——而那恰恰是递归深度、树遍历边界、
索引宽度发生变化的区间。

### 场景本身的有效性

冻结场景必须先证明与真实场景等价，且**等价性要分两层声明**：

| 层次 | 验证内容 | 方法 |
| --- | --- | --- |
| **契约等价** | 消息 schema、字段范围、frame_id、数据类型、时间戳序列 | 短程双链对照 |
| **资源行为等价** | 地图规模增长曲线、分配模式、数据结构形状 | 同负载下对照资源曲线 |

只做契约等价**不足以**支撑资源结论——因为树形结构类数据结构（如八叉树）的性能
高度依赖几何形状，规整的合成几何可能系统性偏乐观。

## 5. 每次 run 必须过的有效性门

任一不过即 `valid=false`；**raw 保留但不计入基线，且不得放宽门后重收**。

| 门 | 检查什么 |
| --- | --- |
| 参数 / graph / endpoint | 被测图与预期一致，明确拒绝不该存在的节点与话题 |
| 计数偏斜 | observation 与 revision 的差值在门内（即节点没掉队） |
| **oracle 逐点比对** | 每 100 revisions 的 counts / bounds / stamp 精确一致 |
| epoch / fingerprint / stamp / revision | 连续性与单调性 |
| checkpoint 时间对齐 | 内存采样时刻与状态时刻的 skew 在门内 |
| 角色 PID / 退出码 | 无提前退出、无强杀、无产物截断 |
| 构建 provenance | 被测 ELF 及其**全部传递依赖**的来源可复算 |
| 配对源身份（仅配对比较） | 比较两侧源码为同一份 |

**正式窗口的计数只认 unique stamp 与 revision delta**，不把 heartbeat 或
state 心跳当作 commit。

## 6. 环境前提

以下是本仓库测量环境的硬约束。**它们直接决定方法选择**——不了解这些会设计出
原理上无法成立的判据。

### 环境事实

测量环境为 **Windows 宿主 + WSL2 / Docker Desktop 的 LinuxKit VM**
（内核 `6.10.14-linuxkit`）。两条实测约束：

**① 没有硬件 PMU。**
`/sys/bus/event_source/devices/` 只有
`breakpoint / kprobe / msr / power / software / tracepoint / uprobe`，**没有 `cpu`**。
`perf stat` 的 `cycles / instructions / branches / cache-references / cache-misses`
一律返回 `<not supported>`，root 亦不可得——这不是 `perf_event_paranoid`
权限问题，是虚拟机没有虚拟化 PMU。容器持有 `cap_perfmon` 也补不了。

**② CPU 时间指标带约 ±30% 争用污染。**
实测依据：四轮 120 秒测量，每轮 workload 逐位相同（各 1201 observations /
1202 revisions / 120.08–120.10 s 窗口、同一 ELF、同一 plateau），目标进程实耗
CPU 时间却是 **12.966 / 13.986 / 14.806 / 16.897 秒**。

同样的功多花 30% 的 CPU 时间——这是宿主争用（缓存/内存带宽）与频率变化造成的
**指标污染**，不是随机噪声，**加样本量无法消除**。

### 分辨率下限

> **本机可分辨的效应量级约 ≥ 30–50%；≤10% 的效应不可分辨。**

大效应可靠：2 倍以上的改进或退化远超污染，结论成立。
小效应无解：3% 量级的差异完全落在污染之下，无论用什么统计方法都分辨不出。

**直接推论：不设计任何依赖 <10% CPU 差异的判据。** 需要判定这个量级时，改用
时间无关量（指令数、分配次数），或换有 PMU 的原生 Linux 环境。

### 指标可信度分类

| 分类 | 指标 | 处理 |
| --- | --- | --- |
| **不可用** | PMU 硬件计数器、IPC、cache miss rate | 取不到数，不要尝试 |
| **不可用** | 预期效应 <10% 的 CPU 时间 A/B 对比 | 无论多少轮次都是掷硬币 |
| **不可用** | `perf stat` 的 `task-clock` 绝对值 | 本质是 CPU 时间，同样被污染 |
| **可信** | RSS / PSS / USS | 页面计数，与调度和争用无关 |
| **可信** | Heaptrack 分配次数、peak heap | 由代码路径决定，与时间无关 |
| **可信** | 精确功能计数（体素数、revision、observation、bounds） | 确定性 + oracle 逐点校验 |
| **可信** | 泄漏与错误的有无（ASan / LSan / Memcheck） | 确定性事实，非时序事实 |
| **可信** | 正确性与等价门（oracle join、fingerprint、epoch） | 同上 |
| **需标注** | **单 run 内**的阶段分解比例 | **可信**——同进程同时刻测量，争用等比影响，比值稳定 |
| **需标注** | 延迟绝对分位数 | 跨 run 漂移 ±30–46%，只能当量级用 |
| **需标注** | CPU 绝对值 | ±30%；仅当效应远超此幅度时结论才成立 |
| **需标注** | 实时可持续性 / backlog | 可信且**保守**：被争用的宿主都跟得上，专用机只会更好 |

### 采集纪律

1. 不新增预期效应 <10% 的 CPU 时间型 A/B 门。
2. 工具返回 `<not supported>` 的记录**保留不删**——它是"检查过且不可用"的证据，
   删除后无法与"从未检查"区分。
3. 报告中的 CPU 与延迟绝对值必须带不确定度，不写超出分辨率的有效数字。

## 7. 结论表述纪律

| 场合 | 要求 |
| --- | --- |
| CPU 与延迟绝对值 | 必须带不确定度；不写超出分辨率的有效数字 |
| 容量结论 | 标注为**本机观测值**并说明方向性（无争用环境下只会更高），不给绝对承诺 |
| 替代方案 | **逐子能力声明**能替代什么、不能替代什么。工具是能力捆，主能力被覆盖不等于全部被覆盖 |
| 换场地取得的证据 | 注明证据来自哪种负载；清扫类工具的 clean 报告**只对实际执行过的路径负责** |
| 未达门的项 | 明确标注未通过，**不计入通过项** |

## 8. 遇到新指标怎么归类

按下列顺序判断，即可确定它该走哪条路线、用什么工具。

**第 1 步：放慢 10 倍会不会变？**

- **不会变** → 时间无关量 → **路线 B**，可自由选择重型工具，只需保证跑满相同
  revision 数。
- **会变** → 时间相关量 → **路线 A**，继续第 2 步。

**第 2 步：能否用零扰动手段取得？**

- **能**（外部读 `/proc`、内核已有计数器） → 直接用，无需校准。
- **不能**（需要在进程内埋点或拦截） → 继续第 3 步。

**第 3 步：扰动是否落在剩余预算内？**

- **是** → 可用，但必须先做扰动校准（同负载下有探针 vs 无探针对照），
  且校准判据本身要满足 §6 的分辨率下限。
- **否** → 缩小规模，或放弃该指标的绝对值、改取**同 run 内的相对量**
  （相对量对等比扰动不敏感）。

**第 4 步：确认覆盖范围**

无论走哪条路线，记录清楚：**跑了什么负载、到什么规模、多长时间**。
指标的结论只在该范围内成立，范围之外不得外推。
