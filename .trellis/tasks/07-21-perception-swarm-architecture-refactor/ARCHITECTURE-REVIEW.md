## 3. 子任务依赖顺序检查

### 3.1 依赖图可视化

```text
C1 (感知输入)
  └─> C2 (本机地图)
       └─> C3 (地图更新语义)
            └─> C4 (通信数据面)
                 └─> C5 (拓扑与角色)
                      ├─> C6 (多机协作)
                      │    └─> C7 (本机执行)
                      │         └─> C8 (集成验收)
                      │              └─> C9a (同机 HA)
                      │                   └─> C9b (跨机 HA)
                      └─> (C5 内部：identity -> link -> graph -> role -> impl)
```

### 3.2 关键路径分析

| 子任务 | 是否在关键路径 | 可并行的任务 | 风险 |
|--------|--------------|-------------|------|
| C1 | ✅ 是 | 无 | 中：涉及感知接口变更 |
| C2 | ✅ 是 | 无 | 高：影响地图语义 |
| C3 | ✅ 是 | 无 | 中：delta 协议设计 |
| C4 | ✅ 是 | 无 | 低：传输层变更 |
| C5 | ✅ 是 | 无 | 高：稀疏拓扑核心 |
| C6 | ✅ 是 | 无 | 中：任务分配逻辑 |
| C7 | ✅ 是 | 无 | 低：本机执行接口 |
| C8 | ✅ 是 | 无 | 高：集成验收 |
| C9a | 否 | 独立于 C9b | 低：协议验证 |
| C9b | 否 | 独立于 C9a | 低：部署验证 |

**发现问题 4**：C5 拓扑与角色是最复杂的子任务，建议拆分为：
- C5a：Identity/session/link 基础
- C5b：三个逻辑图与 route epoch
- C5c：Explorer + pure Relay 实现
- C5d：EdgeAggregator 实现

**建议**：在创建 C5 时拆分为 4 个子任务，降低单个任务复杂度。

**结论**：依赖顺序合理，但 C5 需要拆分以降低风险。

## 5. 缺失约束与风险识别

### 5.1 性能约束缺失

**问题**：PRD 和 Design 中没有明确的性能目标

当前只有：
- "merger 60% 处理成本是基线"（定性）
- "分别测网络字节、CPU、freshness"（方法，无目标）

**缺失**：
- C4 通信数据面：缺少"相对 Phase 3 fullMapToMsg，字节数减少 X%"的目标
- C8 集成验收：缺少"N=5 端到端延迟不超过 X ms"的目标

**建议**：在 C4 和 C8 子任务中补充性能基线和目标。

---

### 5.2 资源约束缺失

**问题**：D-016 提到"资源上限"，但没有具体数值

当前提到但未量化的资源：
- 队列字节上限（D-004 提到但未量化）
- contributor 数量上限（D-009 提到但未量化）
- 单机内存占用上限（未提到）

**建议**：在 C5 拓扑子任务中补充资源预算的具体数值或计算方法。

---

### 5.3 时间约束缺失

**问题**：D-014 定义了时间模型，但没有超时值

缺失的超时配置：
- Freshness 过期时长
- Lease 续约间隔
- Keyframe/resync 超时
- Link health 心跳间隔

**建议**：在各子任务实施时提供默认值和可配置性说明。

---

### 5.4 安全边界模糊

**问题**：D-029 要求验证 trust/auth adapter，但"C1-C8 只验证逻辑"的边界不清楚

**潜在风险**：
- "逻辑 fixture"是否包括签名验证？
- "不选择 PKI"是否意味着 C1-C8 不做任何加密？
- 真实部署时谁负责选择和配置 PKI？

**建议**：在 C4 或独立安全子任务中明确：
1. C1-C8 的 trusted fixture 只验证 identity/session/epoch 逻辑
2. 部署子任务负责选择 DDS-Security 或等价方案
3. 加密是部署要求，不在算法契约中

## 6. 特定决策深入检查

### 6.1 D-008：后端无关 occupancy 契约

**检查点**：是否真的"后端无关"？

现状：
- ✅ 定义了 view/update 抽象
- ✅ OctoMap 通过 adapter 接入
- ⚠️ 缺少"查询能力声明"的具体接口

**潜在问题**：
- Frontier Detector 如果依赖 OctoMap 的"邻居遍历"能力，替代后端可能不支持
- "无法提供某项查询能力时必须显式声明"（PRD R-13），但没有能力枚举

**建议**：在 C2 子任务中枚举必需能力和可选能力。

---

### 6.2 D-012：双层混合交互模式

**检查点**：端点 adapter 与 Relay 的职责边界是否清晰？

现状：
- ✅ Relay 只转发 envelope
- ✅ 端点 adapter 提供 topic/service/action
- ⚠️ "Relay 不代理 action 内部端点"可能导致复杂性

**潜在问题**：
- 如果 action 的 goal/feedback/result 都是领域消息，为什么不能透传？
- 是否意味着每个 action 类型都需要定制的端点 adapter？

**建议**：在 C5 子任务中提供至少 2 个 action 类型的 adapter 示例（探索任务、角色迁移）。

---

### 6.3 D-020 + D-021 + D-022：健康门控三决策

**检查点**：是否覆盖所有降级场景？

现状：
- ✅ D-020：唯一 active mapper
- ✅ D-021：声明 minimum/degraded 契约
- ✅ D-022：分层门控

**潜在问题**：
- 如果 mapper Degraded 但仍满足某些任务的要求，coordinator 如何知道？
- "当前有效 capability"（D-021）如何与"task requirement"（C6）匹配？

**建议**：在 C2 和 C6 的接口设计中明确 capability 的表达方式（枚举？位掩码？结构化对象？）。
