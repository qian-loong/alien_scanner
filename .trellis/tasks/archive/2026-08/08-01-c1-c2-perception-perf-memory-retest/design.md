# C1/C2 感知性能与内存重测 - 技术设计

## 1. 被测边界

**测量对象**：目标节点进程本身。
**排除项**：`ros2 bag record` / `ros2 bag play`、采样器、profiler 均为独立进程，
跟踪其 PID 与退出码用于有效性判定，但**资源数字一律不计入被测节点**。

### 录制与采样合并为同一次运行（已定）

第 1 步的 bag 录制与多节点采样**在同一次 600 s 运行中完成**，不分两次跑。

| 权衡项 | 结论 |
| --- | --- |
| 成本 | 一次运行即得录制素材 + 全节点基线，省一半时间 |
| 代价 | 被测节点的 CPU 数字**含录制器的争用**，略高于无录制时 |
| 补偿 | `ros2 bag record` 本身作为一个 PID **一并采样**，其开销可被量化并在报告中给出 |
| 合理性 | 真实部署中常伴随日志/录制，带录制的数字并非不真实 |

**该偏差必须记入报告**（见 §8）。若后续需要无录制的干净 CPU 数字，可在
第 2/3 步的回放测量中获得——那时不再需要录制。

链路（重构后 `cave_full_ray_scene`，6 个节点 + TF）：

```
cave_publisher ──(洞穴数据)──┐
                              ├──> cave_laser_scan ──(LaserScan)──> pose_gate
fake_odom ──(Odometry)────────┘                                        │
                                                                        ↓
                              perception_input_node (C1) ──(LidarObservation
                                                             + PoseEstimate
                                                             + HealthState)──> perception_local_map_node (C2)
```

## 2. 解耦切点与录制设计

### 切点选择

| 切点 | 录制话题 | 用于测 |
| --- | --- | --- |
| **S1**（gate 前） | `LaserScan`(原始) + `Odometry` + `/tf`,`/tf_static` | C1（真实乱序） |
| **S2**（gate 后） | `LaserScan`(released) + `Odometry` + TF | C1（确定性回归） |
| **S3** | `LidarObservation` + `PoseEstimate` + `HealthState` + **`/tf`,`/tf_static`** | C2 |

> **`/tf` 对 S3 是必需的（实测）**：只回放 observation/pose/health 时，C2 无法解析
> 传感器外参，会**静默丢弃全部观测、一条都不提交**。TF 必须随 S3 一起录。

S1 与 S2 的差别仅在 scan 是否经过 pose gate 排序。两份都录，用途不同：
S1 更接近真机（真实抖动），S2 可复现性更强（固定释放序）。

### 录制与直连的等价性核对

回放必须与直连产生相同的逻辑工作量。核对项：

- observation / revision 计数
- 最终 `known` / `free` / `occupied` 体素数
- `map_epoch`、fingerprint 不变

不一致即说明回放丢数据或时序畸变，该 run 无效。

## 3. 采样设计

### 多节点同时采样（本任务主要新增工程）

现有 `scripts/profile-local-map.sh` 围绕**单个** target PID 构建。需扩展为：

| 能力 | 说明 |
| --- | --- |
| 多 PID 解析 | 由节点名解析到 PID，建立 `节点名 → PID → starttime` 映射并冻结 |
| 多 PID CPU 采样 | `pidstat -p <pid1>,<pid2>,...` 单进程采全部目标 |
| 多 PID 内存采样 | 循环读各自 `/proc/<pid>/smaps_rollup`，取 RSS/PSS/USS |
| 身份校验 | 每个 PID 的 exe 路径与 starttime 必须与冻结值一致，防止 PID 复用 |
| 角色分离 | bag play / 采样器 / profiler 单独记账，不并入任何被测节点 |

**PSS 求和纪律**：系统总内存 = 各节点 PSS 之和。**RSS 不可相加**（共享库被重复
计入）。且求和必须取**同一采样时刻**的快照。

### 采样窗口

沿用既有纪律：预热与收尾另记，只统计正式窗口 `t0–t1` 内的样本；采样器启停紧贴
窗口边界（余量 ≤2 s）。

## 4. 两条测量路线

| | 路线 A | 路线 B |
| --- | --- | --- |
| 频率 | 真实频率（10 Hz） | `bag play --rate` 降频 |
| 工具 | pidstat、smaps_rollup、UST 探针 | ASan、LSan、Memcheck |
| 扰动要求 | 必须 ≈0 | 不限 |
| 覆盖 | CPU、内存占用、泄漏斜率、阶段延迟 | 内存错误、经典泄漏、未初始化读 |

### 路线 B 的设计原则：路径覆盖，不是时间积累

Sanitizer 给每次分配/释放插桩，错误发生的瞬间就报；LSan 在进程**正常退出**时
清点。因此路线 B **不需要时长与循环**，需要的是：

1. **走全真实路径**——单圈真实 bag 即覆盖完整 0→11 m 轨迹的全部路径；
2. **2 份拼接 bag 单圈**——额外覆盖"位姿跳变 → fail-closed → epoch 重置/重建"
   路径（拼 2 份是为路径覆盖，与长跑的趋势积累目的不同）；
3. **干净退出**——SIGTERM 走完析构让 LSan 清点；SIGKILL 会让 LSan 零输出、
   整次测试作废；
4. **阳性对照**——人造泄漏必须被流程抓住，否则阴性结论不可信
   （上轮已知缺口：sanitizer 报告门从未被反例验证）。

### 降频

固定起步值，不再逐工具推导：ASan 先试 `--rate 1.0`，跟不上换 `0.5`；
Memcheck 直接 `--rate 0.1`。放慢不损失路径覆盖，消息一条不少；
每次跑完用计数等价核对兜底。

**降频伴随的参数缩放（实测教训，2026-08-03）**：降频使消息**到达间隔**等比
膨胀，C2 的到达域看门狗会先于任何工具失效——必须把
`sensor_timeout_s`、`health_timeout_s`、`pose_receive_timeout_s`、
`map_freshness_s` 按降频倍数等比放大（语义等价于按 bag 时间度量）。
**`pose_timeout_s` 严禁缩放**：它是 mapper contract fingerprint 成员，改动后
录制的 HealthState 因指纹不匹配被全量拒绝（实测 revision=0）；且其作用在
时间戳域（观测戳−位姿戳），降频本就不改变戳差。缩放后的参数文件随 run 归档
并在报告中声明为偏差。

**Heaptrack 降为条件触发**：仅当长跑斜率 > 0 时加跑一次定位分配栈，
降频按 `工具开销倍数 ÷ 剩余余量` 计算。**Callgrind 移出本任务**
（未验证的研究 spike，需要时另立 finding）。

## 5. 有效性门（两级）

> 全阻塞门是上一轮拖延的根因——它把每个环境怪癖升级成强制工程任务。
> 本轮只保留"结论赖以成立"的门为阻塞，其余降级为标注。

### 阻塞门（不过则该 run 无效）

| 门 | 检查 | 理由 |
| --- | --- | --- |
| bag 可读 | `metadata.yaml` 存在 + `ros2 bag info` 可读 | 不可读 = 无素材 |
| 回放/周期等价 | 计数与基准一致（长跑为每周期提交数 ±5） | 不等价 = 测的不是同一工作量 |
| 阳性对照 | 人造泄漏被抓住 | 流程可信性前提 |

### 标注门（失败记录在报告并评估影响，不作废 run、不当场重跑）

PID 身份（exe + starttime）、角色存活/退出码、`normal_completion`、
residual sweep、构建 provenance。

invalid run 的 raw 保留但不计入基线。

## 6. 泄漏判定

| 维度 | 方法 | 步骤 |
| --- | --- | --- |
| 经典泄漏（malloc 丢失/越界/UAF/未初始化读） | ASan + LSan + Memcheck，真实路径单圈覆盖（§4） | 第 3 步 |
| 可达内存无界增长 | 拼接回放长跑，**周期基线斜率**（见下） | 第 4 步 |

### 周期负载下的泄漏判据（实测机制，2026-08-02 冒烟确认）

拼接回放的每个周期边界，位姿从轨迹终点"瞬移"回起点（10 m >
`position_jump_threshold_m` 2 m），触发 mapper 位姿不连续 fail-closed →
**地图 epoch 重置 → 从零重建**。这是产品的正确行为，由此长跑形态为
"建图↗ → 重置回落"的周期锯齿，判据双重：

1. **各周期基线谷值序列**的线性回归斜率 ≈ 0（阈值沿用 1024 KiB/min）；
2. 周期形态完好——回落缺口即单周期泄漏量（额外收益：覆盖 epoch 重置/
   恢复路径的历史累积类泄漏，正是 §9 论证的最现实泄漏形态）。

**必须同时报告灵敏度下限**——本次窗口实际可分辨的最小斜率，
不得笼统宣称"无泄漏"。

周期等价门：每周期提交数 ≈ 单圈基准 ±5（恢复稳定门的边界损耗，
实测每边界丢 1–4 帧）。

## 8. 与真机的已知差异（必须记入报告）

| 差异 | 影响 |
| --- | --- |
| 仿真传感器替代真实驱动 | 真机的 LiDAR 驱动资源开销未计入 |
| **第 1 步带 bag 录制** | 被测节点 CPU **含录制器争用**，略高于无录制。录制器开销已单独采样并给出；无录制的干净数字见第 2/3 步回放测量 |

## 9. 真实场景的有效负载只有约 20 秒（实测确认）

### 机制

`cave_laser_scan` 是**里程计驱动**的：它没有自己的定时器，只在收到 `/odom`
回调时才有机会发一帧扫描。降采样闸门用 `next_scan_stamp_ns_` 实现
（odom 20 Hz、scan_period 100 ms → 每两条放行一条 = 10 Hz，实测 10.2 Hz，正常）。

**真正让扫描永久停止的是显式锁存**（`CaveLaserScanNode::onOdom`）：

```cpp
if(speed > kMotionEpsilon)      { has_seen_motion_ = true; }
else if(has_seen_motion_)       { scanning_stopped_ = true;   // 单向，永不复位
                                  RCLCPP_INFO(..., "trajectory complete, raw LaserScan acquisition stopped");
                                  return; }
```

因果链：轨迹 20 秒走完 → `LineTrajectory::clampUnit` 把进度钳在 1.0 →
速度归零 → `scanning_stopped_ = true` → 之后所有 odom 在回调首行被丢弃 →
**再无扫描 → C1 无输入 → C2 完全空闲**。

### 实测证据

一次 60 秒录制的消息分布：

| 话题 | 条数 | 时间跨度 |
| --- | ---: | --- |
| `/cave_scene/odom` | 1198 | 0 → 59.9 s（持续 20 Hz） |
| `/cave_scene/perception/pose` | 1195 | 0.2 → 59.9 s |
| **`/cave_scene/raw_scan`** | **42** | **0 → 4.1 s 后完全停止** |
| **`/cave_scene/perception/observations`** | **43** | **0 → 4.2 s 后完全停止** |

odom / pose / tf 持续，是因为 `fake_odom` 与 C1 各自照常运转；只有扫描链断了。
（该次录制在 launch 后 15 秒才启动，故只捕获到运动段尾巴 4 秒；运动段总长
20 秒，完整约 200 帧。）

### 由此确定的测量策略

**场景性质**：固定脚本轨迹——水平定高、10 米直线、20 秒走完。**不是自主探索**。
所有结论必须限定为"该固定场景、运动条件下"，不得外推到长时自主飞行。

| 问题 | 20 秒运动段够不够 | 方法 |
| --- | --- | --- |
| CPU 占用、瓶颈分布 | ✅ 够（约 200 个观测样本） | 真实场景直采 |
| 每单位工作的内存成本 | ✅ 够（地图在增长） | 真实场景直采 |
| 峰值内存、各节点占比 | ✅ 够 | 真实场景直采 |
| **内存泄漏** | ❌ **不够** | **bag 循环回放**（见下） |

泄漏检测在 20 秒窗口内不可行，有两层原因：

1. **统计上**：1024 KiB/min 阈值下只能分辨 340 KiB 增长，回归样本仅约 20 个。
2. **原理上（决定性）**：运动段地图**本来就在增长**，无法区分"正常扩张"与
   "泄漏"。必须有一个"地图不再增长但流水线仍满速"的阶段——真实场景恰恰没有。

### 泄漏检测：重打戳拼接回放（裸 `--loop` 已实测不可行）

延长负载的直觉方案 `ros2 bag play --loop` **不可行**，2026-08-02 冒烟实测：
mapper 对观测与位姿都有时间戳高水位单调检查
（`LocalObservationMapper.cpp:1087` "observation replay or rollback"、
`:1013` "pose rollback, replay, or frame drift"），第 2 圈起时间戳跳回过去 →
**全量拒收**（实测 revision 冻结在 173，观测拒收 350 次、位姿拒收 1660 次，
流水线零工作）。

可行方案是**重打戳拼接 bag**：把源 bag 复制 N 份，第 k 份的全部 header 戳与
TF 戳加 `k × 周期` 偏移后拼接，时间轴变成一条永远向前的直线。冒烟实测
（2 份拼接单次回放）：**零拒收、零 TF 错误**，两段各完整入图（173 + 172 次
提交）。要点：

- session 身份（`session_boot_time_ns` + suffix）与相对量 `freshness_ns`
  **不改**——它们是身份不是时间；
- 源 bag 的 QoS 元数据必须原样携带（`/tf_static` 是 transient_local，
  丢 QoS 会导致 TF 监听收不到、观测被静默丢弃）；
- `/tf_static` 只写一份（静态变换在 tf2 中不受查询时间影响）；
- `--trim-s` 裁掉每段 ~42 s 空闲尾（有效负载仅 ~20 s），周期 62 s → ~26 s，
  工作密度 ×2.5。

每周期边界的位姿"瞬移"触发地图 epoch 重置——这不是缺陷而是产品对物理
不可能事件的正确反应，由此形成的周期判据见 §6。

时间戳门与位姿门是两个独立维度：改戳只修时间轴（时间本就不应倒流），
不骗位姿连续性门（瞬移本就该触发重置）。

### 为什么静态分析与 Valgrind 不能替代长跑

本场景最现实的泄漏形态是**无界增长的可达内存**（缓存/队列无限增长、地图 cell
从不 prune、诊断历史累积）。这类内存指针仍在、退出时正常释放，因此：

| 手段 | 判定 |
| --- | --- |
| LSan / Memcheck | 归为 "still reachable"，**不算泄漏** |
| 静态分析（`-fanalyzer` 等） | **不报**——语法上无泄漏，是逻辑上无界 |
| **长时增长斜率** | **唯一能抓到的手段** |

经典 malloc 泄漏维度上轮虽用 ASan/LSan/Memcheck 得出"无业务泄漏"，但其覆盖
边界是**合成输入激发的路径**；本轮按 §4 用真实 bag 重做该维度（全新采集原则），
上轮结论仅作历史参考、不作本轮证据。

## 10. 录制编排（全部经实测确认）

### 启动顺序：录制器先起，**不使用 `--start-paused`**

```
1. ros2 bag record -o <out> <topics...>        ← 先起，不暂停
2. 校验 record.log 中全部目标话题出现 "Subscribed to topic"
3. setsid 启动 scene
4. t0 = 此刻
```

**依据（实测）**：`ros2 bag record` 默认开启 discovery，按 `--polling-interval`
持续轮询直到目标话题出现；日志中的 `Stopping discovery` 只在**全部**目标话题订阅
完成后才触发。因此录制器可以安全地先于发布者启动。

**实测验证结果**（录制器先起 3 秒，再启动 scene，窗口 50 s）：

| 校验项 | 结果 |
| --- | --- |
| 话题订阅 | 9/9 全部成功，**含 `/tf_static`** |
| `raw_scan` / `scan` / `observations` | **199 / 199 / 199**，三级链路条数一致 |
| C2 state revision | **0 → 198，唯一值 199 个**，连续无缺口 |
| 首个 revision | **0** —— 证明订阅早于 C2 处理第一条观测 |
| 丢包 | **零** |
| 运动段捕获 | 199 帧 / 19.9 s = 10.0 Hz，**完整覆盖 20 s 轨迹** |

> **`--start-paused` 禁止使用。** 它会丢弃 latched 消息——`/tf_static` 是
> transient-local 一次性发布，暂停期间被丢掉，导致 bag **完全无法回放**。
> 它解决的订阅时机问题实际并不存在（见上）。

### 就绪校验（硬性门）

t0 之前必须确认：
- `record.log` 中全部目标话题均出现 `Subscribed to topic`
- 各被测节点 PID 已解析并冻结身份

任一不满足即中止本次 run。

### 丢包对账（硬性门）

不依赖"应该来得及"的推理，**丢没丢必须是测出来的**：

- bag 中 `observations` 条数与三级链路（`raw_scan` / `scan`）一致
- C2 `state` 的 revision 序列从最小值起**连续无缺口**
- 首个 revision 证明录制早于首次提交

不满足即 `valid=false`。

### 收尾（硬性门）

**`ros2 bag record` 在本镜像上完全忽略 SIGINT（实测）**，按 SIGINT 等待会每次挂
90 秒。**SIGTERM 才是其优雅停止路径**：写出 `metadata.yaml` 并 exit 0。

收尾流程：
1. 向录制器进程组发 **SIGTERM**
2. 等待 `metadata.yaml` 出现（该文件是可观测的完成标志，实测约 2 s）
3. `ros2 bag info` 确认 bag 可读
4. 场景按 `setsid` 进程组整体收尾——**`ros2 launch` 不会把信号传播给子进程**
   （实测有节点残留运行 38 分钟）
5. **校验零残留进程**

任一步失败即该次 run `valid=false`。

## 11. 等价性证据必须在窗口之外采集

**规则**：回放等价性所需的证据，一律在 **t1 之后**采集，**不得在测量窗口内引入
任何额外订阅者**。

理由：cookbook 规定路线 A 必须零扰动。窗口内常驻订阅者会让发布端多一次序列化
投递与拷贝，直接违反该要求。`state` 实测为 34 Hz（1694 条 / 49.7 s），持续订阅
并不便宜，而我们只需要它的**最后一个值**。
